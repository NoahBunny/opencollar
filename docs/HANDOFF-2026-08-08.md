# Handoff — 2026-08-08 (device-QA follow-ups: 3 closed)

This session cleared three of the open follow-ups from
`HANDOFF-2026-08-07-device-qa.md` — the ones reachable without re-provisioning

touched, all three compile in both build variants, and the suites are green.

## What landed (all on `feat/ecosystem-review-2026-05-25`)

1. **Status-shadowing trap on the display path** (was follow-up #3). Fix #5 had
   scoped the *signature* rebuild to the top-level JSON object (`StatusCore`),
   but `updateLiveStatus` still read its *display* fields with the first-match
   `parseJson*` helpers — so in direct mode it rendered the `orders`-document
   copies of `paywall` / `task_reps` / `task_done` / `offer` / `offer_status` /
   `sub_tier`. Today those tie with the signed values, so nothing was visibly
   wrong, but it was the same shadowing hazard one schema change from mattering.
   Routed the nine core display fields through `StatusCore.fromWire`; non-core
   fields (`lovense` / `geofence` / `fine` / `body_check`) keep first-match
   because in direct mode they exist *only* inside `orders`. Fail-safe fallback
   to first-match if the body won't parse. Hardened
   `StatusCoreTest.rebuiltCoreUsesTheSignersNativeTypes` to pin the native types
   the new display casts depend on.

2. **Release Forever teardown on Android 16/17** (was follow-up #4). The
   self-destruct shelled `dpm remove-active-admin`, which A16/17 refuse for a
   non-test admin, so teardown stalled on a manual Settings deactivation both QA
   sessions. The Collar now removes **its own** admin via
   `DevicePolicyManager.removeActiveAdmin(adminComponent())` (works on every API
   level for a same-package caller; `release_authorized=1` keeps `onDisabled` a
   no-op). Because one package can't remove another's admin, **Bunny Tasker now
   removes its own** admin from `BunnyService`'s watcher on seeing
   `focus_lock_release_authorized==1`, then stops the watcher. The shell `dpm` /
   `pm` calls stay as best-effort fallbacks (the ADB bridge remains the reliable
   uninstaller).

3. **Cold-onion wake now shows progress** (was follow-up #1). The first cold
   order blocks up to 120 s in `wakeAndAuthorize`; the old one-shot "Waking
   Collar…" was overwritten by the next timer tick and the UI looked dead. Added
   a depth-counted `beginWakeIndicator` / `endWakeIndicator` pair: a 1 s ticker
   owns the status line with a counting-up elapsed timer while any wake is in
   flight, and the timer tick + `updateLiveStatus` yield the line to it. Inert in
   default (Tor-OFF) builds.

4. **Distinguishable bunny slot names** (was follow-up #2). Slots defaulted to
   the literal "bunny", so the status line couldn't tell whose lock/balance you
   were seeing — the ambiguity that hid the fix-#7 leak. New slots default to a
   stable per-slot tag (`bunny-<fp>` for a direct pair, `bunny-<mesh>` for a
   relay mesh); the Advanced → Bunnies rename still applies. Also fixed the
   Bunnies dialog not redrawing after a rename/removal.

5. **Safety-floor gap: admin-tamper handlers didn't honor the terminal
   `released` state.** Found while tracing #4. The `released` flag (set by the
   safeword, never cleared short of a factory reset) was honored by the
   enforcement loop, jail, order-apply and bridge — but the Collar's and
   companion's `AdminReceiver.onDisabled` and the companion's mutual-admin
   monitor gated only on `release_authorized`, which `doReleaseForever` deletes
   at the end of teardown. So a released device whose admin was later removed
   could be re-locked (Collar set `active=1` + jail) or fire false tamper alerts.
   All three now honor `released` too. The same audit found the Collar's **direct
   `/api/*` HTTP order path** also didn't honor `released` (the mesh and legacy
   apply paths did), so a signed `/api/lock` over LAN could set `active=1` on a
   freed device — now gated with a blanket `isReleased()` refusal mirroring
   `handleMeshOrder`. See CHANGELOG for the full write-up.

6. **Same floor gap in the desktop collars.** `focuslock-desktop.py` and
   `focuslock-desktop-win.py` fired liberation only on the direct `release-device`
   *action*; a release arriving as order *state* (gossip `apply_remote` or a vault
   order snapshot — how a phone safeword propagates) just set the `released` key
   and the poll loop kept enforcing until restart. `poll_status` now honors
   `released` at runtime on every path. NOTE: the Windows `.exe` needs a
   `build-win.py` rebuild (not possible from this environment) to ship; the Linux
   collar deploys as source via `re-enslave-desktops.sh` (hash-diff, no version
   bump).

- Possible design decision (not a clear bug, deliberately left alone): the Lion's
  **Release Forever** sets only `release_authorized`, not the terminal `released`.
  So if its uninstall fails (app-uid `pm uninstall` needs the bridge/device-owner),
  the device is left merely unlocked, not floor-released, and could be re-locked.
  The safeword path DOES set `released`. Making Release Forever set it too would be
  more robust but is terminal-until-factory-reset — an operator call.
